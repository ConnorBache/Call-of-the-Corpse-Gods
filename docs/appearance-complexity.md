# Native appearance authoring complexity

The appearance modules own cosmetic data only. They never accept a `Run`, dispatch a gameplay command, sample simulation RNG, or write a game save. Source: frozen v48 `appearance-config.ts`, `appearance-store.ts`, and `appearance-editor.ts`.

## Bounds and operations

Let B be normalized JSON UTF-16 character count, C = 1,665 authored controls, d <= 32 JSON nesting levels, H <= 80 retained history snapshots, K <= 50 saved presets, G the number of catalog groups in the selected category, and T displayed text characters. A profile is bounded to 2,000,000 source-compatible UTF-16 characters; any single string is bounded to 100,000 characters and any object/array to 10,000 entries. Source ASCII/custom-glyph, color, font-list, enum, number, and cross-field brightness validation remains in force. Input files are additionally bounded to 8,000,000 UTF-8 bytes before allocation can grow further.

- Parsing/merging/validating a profile takes O(B + C*d) time and O(B + d) auxiliary storage. Defaults and control metadata parse once into immutable `OnceLock` values. Unknown JSON fields are preserved, so cost is charged against the full input, not just known controls. Serde parsing has its own recursion guard before explicit depth validation.
- Property edit/reset clones the complete normalized profile, changes a leaf, and validates the result: O(B + C*d) time and O(B) extra storage. Field access splits a path and traverses up to d objects; this is not a constant-time renderer-profile lookup. Typed getters do not clone the profile. Material inheritance copies one fixed-size material object.
- A committed edit compares serialized profiles and, when needed, serializes/clones a history entry: O(B + C*d), not O(1). Stored entry sizes are cached. Trimming uses deque front removal and visits only removed entries. Combined undo/redo history is capped at 80 snapshots and 8,000,000 serialized UTF-16 characters. The cap is on serialized history, not an assertion that Rust object heap overhead equals that number of bytes. Current/original/preview/gesture profiles and temporary serialization buffers are separate O(B) storage.
- Undo/redo clones/serializes the current snapshot and transfers the nearest history entry: O(B) plus removed-entry destruction. A grouped input gesture retains one before-snapshot and pushes one history entry when ended. Text-box edits commit once on Enter; discrete +/- clicks are individual undoable edits.
- Preset save/rename/update/delete/startup selection clone the bounded library and serialize the complete next library. Worst case O(K*B) time and temporary memory before enforcing the 2,000,000-character aggregate library limit. Explicit persistence writes a same-directory `create_new` temporary file, syncs it, and renames only after a successful write. Failed writes do not replace the in-memory library. Directory sync is attempted on Unix; filesystem durability and replacement semantics are platform-dependent and are not claimed certified on every platform.
- The editor filters C controls by category/group/query. Its straightforward group discovery is O(C*G), followed by O(C*Tquery) substring matching; it is intentionally not labeled O(C) while using linear duplicate-group checks. Current maximum catalog size is fixed at C. Display only paints five font rows or six ordinary rows. Profile status compares serialized configurations, adding O(B) per editor repaint. Rendering adds the software painter's framebuffer O(P), glyph raster/cache costs, and displayed glyph-pixel costs described in `desktop-complexity.md`.
- The font sample paints three fixed ASCII lines through the same map-identity renderer. Cold font/atlas raster costs remain the renderer's responsibility; this editor does not claim those calls are O(1).

## Evidence and scope

`tools/export-appearance.mjs` reads the frozen build without modifying it. It verifies the existing default asset, exports all 1,665 controls, 17 parse/edit/reset oracle cases, and 41 store transitions. Each transition compares active profile, edited profile, and dirty/preview/history/comparison/saved/default status. Separate native tests cover failed persistence, corrupt-file preservation, import/export limits, entity/material inheritance, repeated edits, cancel/hide, reset, confirmation, search/scroll bounds, and fixed editor geometry under extreme settings.

These are correctness tests and asymptotic bounds, not quiet-machine performance measurements. Software-rendered screenshots do not certify OS clipboard, desktop fullscreen, file-dialog behavior, or identical platform font outlines. Native UI uses an explicit path/pasted JSON/drag-and-drop import instead of a browser file picker. See `appearance-native-coverage.md` for renderer coverage and retained-only options.

## Profile-aware detached lighting

`appearance_light.rs` translates `createVisualLightField` and deterministic source flicker. Let N = grid cells, S = detached light sources, F = summed source-footprint entries, and D = max(width, height). Without radius expansion, expected cost is O(N + F + S) time and O(N + S + largest footprint) extra memory. Source deduplication uses a hash index for lookup and a separate ordered vector to preserve first-seen emitter order. Each energy update and final exposure explicitly rounds through f32 where the source writes Float32Arrays. Illumination remains f64 and unchanged.

When visual radius exceeds one, each eligible known-origin source may visit O(N) candidate cells and raycast O(D) known cells per candidate: O(N + F + S*N*D) worst-case time. Adjacent checks prevent diagonal rays from leaking through unknown corners, walls, trees, or closed doors. Only currently observable cells enter expansion; remembered terrain cannot authorize a ray. No new visibility, terrain, or actor facts are generated. Unknown-origin emitter groups remain distinct using the detached emission-group identity; their redacted coordinates are never reconstructed.

Animated lighting requires rebuilding these detached fields at presentation timestamps and reapplying display colors; that cost must be included for each animation repaint, not charged only on gameplay turns. `animated` scans six fixed registered categories and ignores unknown future JSON source payloads. The fixture exporter covers 41 full source light fields plus 54 deterministic flicker samples, including every global/per-category control, overlap blend modes, darkness, fire/fixture deduplication, burning liquid, unknown/remembered blockers and diagonal corners. Exact output energy/ambient/illumination and input immutability are tested. Unknown-origin flicker uses the already-redacted (-1,-1) phase; exact hidden-coordinate phase parity is unavailable without violating the knowledge boundary.

## Pure UI role resolution

`typography_ui` applies five changed-from-source-default fields to an explicit caller baseline in O(1) at fixed profile depth. Chronicle derived metrics are O(1). Font candidate parsing is O(F²) with duplicate elimination, bounded by validated font-family text; resolve once per profile update rather than per glyph. Source consumer matrix and 53 CSS fixture cases: `appearance-source-consumers.md`.

## Responsive Pack/Inspector geometry and text

`modal_ui::Frame`, PackLayout and hover/Inspector rectangles are O(1), computed from profile fields only. Pack configure scans T characters of detached group labels/descriptions/action labels and caches D distinct scalar advances: O(T + D*F) time and O(D) metric memory, where F is bundled fallback-face lookup/metric work. Profile changes invalidate role metrics; unchanged profiles reuse per-character measurements. No font rasterization is needed for measurement. Text wrapping currently scans candidate strings, O(T²) worst-case time and O(T) output; detail/button layout may invoke it multiple times per input/paint, bounded by the observed inventory (at most100 records) and selected-item text. Inspector wrapping has the same bound plus existing fontdue metrics work; no Run/history payload enters these routines. Styled paint cache-miss rasterization remains in Painter. These are complexity bounds, not performance measurements. Source-controlled row/window dimensions never depend on inventory length or prose length; content overflow changes scrolling only.
