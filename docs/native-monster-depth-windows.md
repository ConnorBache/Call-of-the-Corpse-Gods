# Native monster depth windows, simulation revision 30

The designer requested monsters to be available two depths earlier and two depths later. Revision30 expands all 55 normal roster leaders' frozen first/last depths by2, clamped to1..40. Their two paired followers follow the leader's expanded range. The frozen JS source and frozen population JSON remain unchanged. The checked-in baseline roster is extracted read-only by `tools/export-ordinary-roster.mjs`; native `ordinary_roster.rs` performs the expansion and same thematic recipe rules.

The introduction-weight ramp starts at the new first depth so earlier eligibility always has positive weight. No creature stats, heart rewards, per-floor blessing budgets, horde size weights, exact-budget solver targets, Banshee cap, habitat requirements, pair chance or placement rules change. Floor1 retains its low/medium danger gate. Eligible species are not guaranteed to occur in every generated floor: weighted selection, reward feasibility, habitat and placement still apply. Existing geometry/machine reservations use the frozen catalog and all old ordinary recipes remain available, so previously feasible reserved budgets remain feasible. Special setup windows, corpse props, Sphinx and Godbeast placement are unchanged.

The9 Ichor event species also have explicit first/last windows. Revision30 expands these by2 with the same clamps, uniform selection and single serialized random draw per successful emergence. Mercuria's well, ichor, cadence and floor4 event gate remain required. Zillennia uses a deterministic single quality per depth rather than an eligible pool: its quality bands remain unchanged pending designer direction on selecting among overlapping qualities. Growth/evolution forms keep their existing triggers; Pale offspring conditional appearances follow the expanded Birther windows transitively.

New runs use simulation revision30. Revision29 saves, time-travel snapshots and seed replays retain original ordinary/Ichor selection. Revision-aware startup, lazy floor generation, replay creation/restart and storage validation support both revisions. Unversioned replay imports that explicitly opt out of requiring revision retain historical revision29 behavior. Unknown versions are rejected. `plan_budgeted_hordes` and `populate_hordes` remain explicitly documented frozen differential APIs; current startup uses their revision-aware counterparts. There is no process-global generation switch.

The embedded manual is synchronized from actual native candidates, including pair followers, conditional Pale births and Ichor windows. Run `tools/cargo.sh run -p corpse-core --example update_manual_depths -- crates/corpse-desktop/assets/manual.json` after exporting frozen prose. `shipped_manual_matches_runtime_eligibility` guards the shipped data. This describes current new runs; loaded revision29 runs intentionally retain historical generation.

## Verification

`tests/ordinary_roster.rs` covers all40 depths and both habitat states: widened boundaries, old-recipe preservation, reward/size/pair/Banshee/habitat/first-floor invariants, invalid depths, deterministic repeated planning, revision29/30 save/lazy generation/replay restart, Ichor pool selection and manual alignment. A separate fixed-seed smoke test successfully places the widened population through all40 generated floors. `artifacts/ordinary-roster-distribution.csv` records320 plans (4fixed seeds ×2 habitats ×40depths); this is a bounded deterministic smoke sample, not proof of a uniform occurrence distribution. It validates exact blessing totals, average group size1.5..2.5, positive-group minimum and Banshee caps. Candidate species counts increase from7–8 to10–13 (floor1:7 to9), subject to the existing floor1 gate. Frozen population and seed replay differential tests remain independent regression coverage.

## Complexity

Let K≤55 be authored normal leaders, P=2 pairs, M≤5 maximum members, S≤4 size choices, R≤K²S attempted recipes, C≤R retained recipes, and D=40 depths. A depth/habitat cache miss filters K definitions then expands the same ordered recipes. Each attempt constructs O(M) members, sorts an O(M) dedup key in O(M log M), scores/rewards O(M), and finds introduction metadata in O(M(K+P)). Expected hash membership is O(M); adversarial hash collisions can add O(CM). Thus expected construction O(K + R[M log M + M(K+P)]) time, collision-worst O(K + R[M log M + M(K+P+C)]), and O(CM + K) additional memory including retained strings/keys. At most2D immutable recipe pools are cached, O(DCM) retained memory. Cache hits are O(1) before the unchanged horde planner; no rendering, pathfinding, LOS or gameplay RNG is involved. Baseline JSON decoding occurs once, O(input bytes) time/memory. Horde-planner feasibility costs are unchanged in structure but C increases; see generation complexity documentation for solver state dimensions. The320-plan debug sample completed in0.89s in this environment, an observation rather than an asymptotic or platform guarantee.

Ichor pool filtering is O(F), F=9, with O(F) temporary references per successful spawn; selection and draw count are unchanged. Manual synchronization is build-time only: scans D candidate pools and E=81 entries, retains O(DE+DCM) data; its JSON parse/write costs are O(B) for B asset bytes. Native manual rendering costs are covered separately. Replay/save selection adds O(1) revision checks; existing full startup/save and time-travel costs remain unchanged.
