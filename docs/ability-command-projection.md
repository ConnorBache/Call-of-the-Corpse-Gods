# Desktop ability command projection

Frozen sources: `src/main.ts` currentCrafts/ability refresh, `crafting.ts` craftAbilities/useCraftAbility, `ability-explanation.ts` craft presentation/explanation, and `ability-presentation.ts` Adaptive Armor resources. Native UI projects ordinary player abilities followed by equipped inventory Fury/Zeal enhancement slots. Stable command IDs are `craft:<item>:<slot>`; inventory order and slot indices are retained. Inspection and input share this projection. Crafting/inventory/equipment mechanics are unchanged. Active targeted toggles dispatch OFF before target selection. Adaptive Armor has a compact type count; every live type, heart count and DR is appended to the existing scrollable detail description.

## Complexity

Let A be player ability count, C the fixed catalog size, I inventory items, E total equipped enhancement slots, H adaptive creature-type entries, N current-floor actors, B maximum abilities/traits per actor, F stored floors, D maximum LOS ray length, and T output text bytes. Projection runs on UI observation refresh and command selection, never a simulation turn by itself. Ordinary rows cost O(A*(C*(A+1)+H+F)+T) conservatively: each catalog lookup scans C; reaction summaries scan catalog and player IDs; Adaptive text enumerates H. Equipment rows cost O(I + E*(C + F + N*(B+F+D)) + T) conservatively: craft-name resolution scans C and paid Zeal availability may scan actors and test aura traits/LOS. Core trait membership, stored-floor lookup, and LOS are included; early exit commonly reduces this bound. Extra memory O(A+E+H+B+T), including temporary adaptive rows. There is no caching, randomness, simulation mutation, or extra visibility flood. Catalog is fixed; inventory/actors/adaptive types follow run bounds rather than a new UI cap. Deactivation helper scans O(A) active IDs with O(1) additional memory. Direct crafted-ID inspection recomputes craft rows at the same bound.

Scrollable detail wrapping is linear in emitted text plus renderer glyph work; every dynamic entry remains in the description and can be reached through the existing offset, independent of compact cost truncation. This is asymptotic analysis, not measured timing. Validate with focused ability_ui tests plus the full desktop/workspace suites; platform execution still needs desktop smoke tests. Tests exercise crafted order/IDs/native activation effects, cost gates/silence, unequip disappearance, all 20 adaptive entries, and active targeted toggle routing. They are source-backed assertions, not differential JS execution or platform verification.
